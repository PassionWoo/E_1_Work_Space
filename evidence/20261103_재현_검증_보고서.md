## 3. Docker 이미지 제작 및 NGINX 동작 검증

기존 프로젝트의 `02_webserver/Dockerfile`은 다음 구조다.

```dockerfile
FROM nginx:alpine
COPY site/ /usr/share/nginx/html/
EXPOSE 80
```

```powershell
docker build -t codyssey-web:1.0 .\02_webserver
docker run -d --name codyssey-web-8080 -p 127.0.0.1:8080:80 codyssey-web:1.0
curl.exe -i http://127.0.0.1:8080/
```

재검증에서 커스텀 이미지 빌드가 성공했고, `curl.exe`에 **`HTTP/1.1 200 OK`** 및 다음 HTML이 출력됐다.

```html
<h1>Hello from Codyssey Docker!</h1>
```

브라우저에서도 웹페이지가 표시되어 해당 화면을 별도 캡처로 남겼다. `127.0.0.1:8080:80` 매핑은 호스트의 루프백 인터페이스 8080번 포트를 컨테이너 80번 포트에 연결한다. Dockerfile의 `EXPOSE 80`만으로 호스트 포트가 자동 공개되지는 않으며, 실제 게시에는 `-p`가 사용됐다.

## 4. 네트워크 네임스페이스 비교와 포트 충돌 진단

### 4.1 네트워크 네임스페이스의 구분

동일한 `codyssey-web:1.0` 이미지를 사용하는 두 컨테이너에서 다음 명령어를 실행했다.

```powershell
docker exec codyssey-web-8080 readlink /proc/self/ns/net
docker exec codyssey-net-test readlink /proc/self/ns/net
```

당시 출력된 네트워크 네임스페이스 inode 표기는 각각 **`net:[4026532378]`**, **`net:[4026532454]`**였다. 즉, 이 관찰 시점에 두 컨테이너의 해당 프로세스는 서로 다른 네트워크 네임스페이스에 있었다.

`docker inspect`의 포트 설정에서도 8080 컨테이너는 호스트 포트 `127.0.0.1:8080`이 연결된 반면, `codyssey-net-test`는 컨테이너 내부 포트 `80/tcp`만 표시되며 호스트 게시 포트가 없었다.

**원리:** 네트워크 네임스페이스는 네트워크 인터페이스·라우팅 테이블·포트 공간 등을 분리하는 Linux 커널 기능이다. 단, 서로 다른 네임스페이스가 관찰됐다는 사실만으로 **두 컨테이너 간 통신이 전혀 불가능함**을 입증한 것은 아니다. 실제 통신 가능성은 Docker 네트워크 연결 및 방화벽·라우팅 설정에 좌우된다.

### 4.2 고의로 발생시킨 8080 포트 충돌

기존 8080 포트가 사용 중인 상태에서 동일한 호스트 포트로 새 컨테이너를 실행하려 했다.

```powershell
docker run -d --name codyssey-port-conflict -p 127.0.0.1:8080:80 codyssey-web:1.0
```

실제로 다음 오류가 발생했다.

```text
Bind for 127.0.0.1:8080 failed: port is already allocated
```

오류의 원인을 추측으로만 처리하지 않고 단계적으로 확인했다.

```powershell
docker ps --filter "publish=8080"
Get-NetTCPConnection -LocalPort 8080 -State Listen |
  Select-Object LocalAddress,LocalPort,State,OwningProcess
Get-Process -Id 12876
```

- Docker 조회에서는 기존 `codyssey-web-8080` 컨테이너가 8080 포트를 게시 중이었다.
- Windows TCP 조회에서는 포트 8080의 수신 소켓을 확인했고, 당시 소유 PID는 **12876**이었다.
- 해당 PID의 프로세스 이름은 **`com.docker.backend`**로 확인됐다. 이는 Docker Desktop의 호스트 측 포트 처리 프로세스이며 NGINX 컨테이너 프로세스와 동일한 것은 아니다.
- 충돌로 생성 상태에 머무른 `codyssey-port-conflict`를 삭제하고, 사용하지 않는 8081 포트로 새 컨테이너를 실행했다.
- 이후 **8080과 8081 모두 HTTP 200 OK**를 반환했다.

**진단 원리:** 포트 충돌은 이미 사용 중인 호스트 IP·포트 조합에 다른 수신자가 바인딩하려 할 때 발생한다. 올바른 조치는 점유 주체를 확인한 뒤 기존 서비스를 중지하거나 다른 호스트 포트를 지정하는 것이다. 무작정 프로세스를 종료하지 않았다.

## 5. Ubuntu 컨테이너에서 Linux CLI와 권한 검증

Ubuntu 24.04 컨테이너 `codyssey-cli-lab`에서 `pwd`, `ls -la`, `mkdir`, `cp`, `mv`, `rm`, `cat`, `chmod` 등을 실행했다. 파일·디렉터리 생성과 이동·삭제 결과를 실제로 확인했다.

권한 검증에서는 숫자 표시만 읽지 않고 **일반 사용자 권한으로 접근을 시도**했다.

| 상태 | 파일 권한 | 비관리자 UID 65534의 `cat` 실행 결과 |
|---|---|---|
| 권한 변경 전 | `644` | 파일 내용 읽기 성공 |
| `chmod 600` 후 | `600` | `Permission denied`, 종료 코드 `1` |

이는 `644`의 타인 읽기 권한이 `600`에서는 사라진다는 설명과 일치한다. `root`만으로 파일을 읽으면 권한 제약을 충분히 검증하지 못할 수 있으므로 비관리자 UID를 사용했다. 디렉터리에서도 `755`에서 `700`으로 모드를 변경하고 표시를 확인했다.

## 6. 컨테이너 실행·중지·재시작 및 운영 정보

```powershell
docker ps -a
docker logs --tail 20 codyssey-web-8080
docker stats --no-stream
docker stop codyssey-net-test
docker ps -a --filter "name=codyssey-net-test"
docker start codyssey-net-test
docker ps --filter "name=codyssey-net-test"
```

- `docker ps -a`에서는 실습 당시 NGINX 컨테이너 3개와 Ubuntu CLI 컨테이너 1개가 실행 중인 것을 확인했다.
- NGINX 액세스 로그에는 `/` 요청의 **200** 응답이 기록됐다. `favicon.ico` 요청은 파일이 없어 **404**를 반환했으나 메인 페이지의 동작 실패를 뜻하지는 않는다.
- `docker stats --no-stream`으로 컨테이너별 CPU·메모리·I/O의 측정 시점 값을 확인했다.
- `codyssey-net-test`에 `docker stop`을 실행하자 **`Exited (0)`**으로 바뀌었고, `docker start` 후 **`Up`**으로 복귀했다.
- 재시작 전후 컨테이너 ID는 동일한 **`20e2dee86a10`**이었다.
- 재시작 전후 `readlink /proc/self/ns/net` 결과도 `net:[4026532454]`로 같았다. 다만 inode 번호는 재사용될 수 있으므로 **동일한 네임스페이스 객체가 중지 기간 동안 유지됐다고 단정하지 않는다**.

**개념 구분:** `stop`은 실행 중인 주 프로세스를 종료하고, `start`는 기존 컨테이너를 재가동하며, `rm`은 컨테이너 객체를 삭제한다.

## 7. 바인드 마운트: 호스트 파일 수정의 반영

원본 소스코드를 훼손하지 않도록 `evidence/bind-lab/index.html`을 별도로 만들었다. 이를 NGINX 컨테이너에 읽기 전용으로 연결했다.

```powershell
$bindPath = (Resolve-Path ".\evidence\bind-lab").Path
docker run -d --name codyssey-bind-test -p 127.0.0.1:8082:80 --mount "type=bind,source=$bindPath,target=/usr/share/nginx/html,readonly" codyssey-web:1.0

docker inspect --format '{{json .Mounts}}' codyssey-bind-test
curl.exe -i http://127.0.0.1:8082/
```

마운트 정보에서 다음 값이 확인됐다.

```json
{"Type":"bind","Destination":"/usr/share/nginx/html","RW":false}
```

처음 HTTP 응답은 다음과 같았다.

```html
<h1>Hello from Codyssey Docker!</h1>
```

Windows에서 실험용 HTML을 변경한 뒤, `docker exec ... cat`과 8082 HTTP 응답에서 **이미지 재빌드·컨테이너 재시작 없이** 변경된 내용을 확인했다.

```html
<h1>Bind Mount Updated Successfully!</h1>
```

### 부수적으로 발견한 UTF-8 BOM 문제

Windows PowerShell 5.1에서 `Set-Content -Encoding UTF8`로 저장하자 HTML 앞에 BOM이 추가된 것이 HTTP 응답에서 관찰됐다. 이후 다음 방식으로 BOM 없는 UTF-8 파일을 기록했다.

```powershell
$path = (Resolve-Path ".\evidence\bind-lab\index.html").Path
[System.IO.File]::WriteAllText($path, "<h1>Bind Mount Updated Successfully!</h1>`n", [System.Text.UTF8Encoding]::new($false))
```

응답은 계속 **200 OK**였고, `Content-Length`는 **46바이트 → 42바이트**로 바뀌었다. 이는 BOM 3바이트 제거와 줄바꿈 CRLF→LF 전환에 따른 1바이트 차이로 설명된다. 이 사례는 서버 연결 문제가 아니라 **파일 인코딩 문제**였다는 점을 구분했다.

## 8. Docker Named Volume: 컨테이너 삭제 후 데이터 보존

Docker 관리형 Named Volume `codyssey-volume-lab-20261103`을 새로 만들었다.

```powershell
docker volume create codyssey-volume-lab-20261103
docker volume inspect codyssey-volume-lab-20261103
```

`Driver`는 `local`, `Mountpoint`는 `/var/lib/docker/volumes/codyssey-volume-lab-20261103/_data`로 출력됐다.

**재현한 핵심 실험:**

```powershell
docker run -d --name codyssey-volume-a --mount type=volume,source=codyssey-volume-lab-20261103,target=/data ubuntu:24.04 sleep infinity
docker exec codyssey-volume-a sh -c 'echo Codyssey-Volume-Persistence-Test > /data/test.txt'
docker exec codyssey-volume-a cat /data/test.txt
docker rm -f codyssey-volume-a
docker ps -a --filter "name=codyssey-volume-a"
docker run -d --name codyssey-volume-b --mount type=volume,source=codyssey-volume-lab-20261103,target=/data ubuntu:24.04 sleep infinity
docker exec codyssey-volume-b cat /data/test.txt
```

컨테이너 A는 삭제된 것이 목록에서 확인됐다. 이후 새 컨테이너 B에서 다음 문자열을 다시 읽었다.

```text
Codyssey-Volume-Persistence-Test
```

추가 점검에서 B의 마운트는 `"Type":"volume"`, `"Name":"codyssey-volume-lab-20261103"`, `"Destination":"/data"`로 확인됐으며, `/data/test.txt`는 **33바이트** 파일로 남아 있었다.

**해석:** 이 실험에서는 컨테이너 A의 삭제와 Named Volume의 삭제가 독립적이었고, 해당 볼륨 데이터가 새 컨테이너 B에서도 유지됐음이 입증됐다. 볼륨 자체를 삭제하거나 Docker의 저장소를 초기화한 경우까지 영구 보존된다는 의미는 아니다.

- 로그에서 `password|token|secret|authorization|PRIVATE KEY|ghp_|github_pat_|@` 문자열을 찾았을 때 04번 기록의 22·35번 줄이 탐지됐다. 후속 패턴 검사에서 22번 줄은 PowerShell의 `@{}` 구문, 35번 줄은 `Select-String` 검색 명령과 부합했다.
- 이메일 형식, `ghp_`, `github_pat_`, PEM 개인키 헤더 패턴을 추가 검색한 결과 **일치 항목이 출력되지 않았다**.

**보안 한계:** 자동 패턴 검색은 전체 로그의 무해함을 보증하지 않는다. 공개 전 화면 캡처, 사용자 디렉터리 경로, 호스트명, 원격 저장소 및 CLI 출력의 계정 식별정보 등을 사람이 직접 검토해야 한다. 원본 증거는 보존하고, 공개용 마스킹본이 필요하면 별도로 만든다.
